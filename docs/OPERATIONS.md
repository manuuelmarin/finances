# Backup, rehearsal and cutover

Finanzas 3.9.0 uses API 3.3.0 and workbook model 3. Keep the existing test deployment and `ENVIRONMENT=test` while validating this release. Publishing Pages or changing this repository does not update a private Apps Script deployment or activate the principal workbook.

## Before changing a workbook or deployment

1. Stop new submissions on every device. Inventory pending requests by device, workbook and deployment. For a submitted or uncertain UUID, query its **original deployment** for status and preserve the same envelope and receipt. Resolve every pending request before changing a deployment, workbook or environment; never replay test requests against the principal.
2. Make a dated **native Google Sheets copy of the complete workbook**, including inputs, formulas, hidden technical sheets, named ranges and calculation outputs. Keep the original workbook untouched. Also retain the original XLSX as historical evidence. Record the workbook revision and `start`, `asof` and `valuation` cutoffs privately.
3. Save the exact deployed `Code.gs`, `Bridge.html` and `appsscript.json`, plus the Apps Script project/deployment version and private configuration in a restricted location. Record Script Properties (`OWNER_EMAIL`, `ENVIRONMENT`, workbook IDs and any other configured values), the owner account and deployment URL privately. A Sheets copy is not a verified backup of Script Properties or deployment settings; a bound script may copy with its workbook. Inspect any copied script, properties and triggers, then configure and verify the isolated project explicitly. Never commit IDs, emails, private URLs, credentials, financial rows or these records to this repository.
4. With the original read-only, reconcile account opening and actual balances, product units and valuation, invested capital, outstanding debt, settings and report cutoffs against the backup. Record discrepancies before any update. Run `comprobarCierre()` / **Comprobar sistema** for a read-only structural check; `ok:true` alone is not evidence that every readiness or source check passed.

## Disposable restore rehearsal

Restore the backup to a **new test-only workbook** and configure a separate private test Apps Script project for that copy. Verify Script Properties and owner access explicitly, then check all financial inputs, formulas, named ranges, audit/receipts and read results against the saved baseline. Keep requests from the original deployment out of this copy.

On the disposable test pair, exercise the changed paths on desktop and phone: archive and restore behavior, templates and plans, historical chunks and their cutoffs, transfers and cancellation, and an offline pending-request recovery. Review the operation before sending and reconcile the resulting accounts, units, value, capital, debt and settings. Cancel test entries and verify the final financial inputs against the baseline. A browser simulation cannot establish physical-phone acceptance; use the real owner account and phone for that check. Preserve the rehearsal record privately and discard the disposable pair only after every pending request is resolved.

If a native formula migration is needed, use **exact-source guarded wrappers** only on the backed-up, disposable copy first. The guard must match the expected original formula before replacing it; a mismatch requires review, not a forced overwrite. After **all** transfers have been cancelled and financial inputs reconcile, restore the guarded base formulas and verify equivalent native financial results. The private workbook backup retains the original structured-reference syntax; an API restoration may convert it to equivalent A1 formulas because writing the original syntax through the Sheets API can cause a parse error. Do not claim byte-identical formula restoration or apply an unverified migration to the principal. Keep the full financial backup until calculations and summaries match.

## Principal activation, when separately authorized

Reconcile the latest principal workbook with the source XLSX and any transactions since the last comparison. Make a fresh full backup and resolve all pending UUIDs on their original deployments. Use a **separate Apps Script project and private deployment** for the principal, distinct from the test project, and a distinct principal workbook. Configure its owner, `PRODUCTION_SPREADSHEET_ID` and `ENVIRONMENT=production` privately; retain the separate test setup. Verify `TEST_SPREADSHEET_ID` and `PRODUCTION_SPREADSHEET_ID` differ. Prepare and inspect the principal with the documented read-only checks before changing the app's deployment selection. Never run disposable financial tests or activate the daily test price routine on the principal.

After an authorized switch, compare accounts, units, value, capital, debt, settings and cutoffs with the saved record. If a write is uncertain, stop submissions, retain the UUID and query the **original deployment** before retrying the identical envelope. For recovery, preserve the current workbook and journal, restore a copy into another workbook, re-enter private Script Properties/deployment settings, validate formulas and reconcile later audit/receipts before resuming. Never bulk-resend pending requests.

The repository's [main ruleset](../.github/rulesets/main.json) is a proposed policy, not active protection. An administrator must import and verify it separately; see [branch protection](BRANCH_PROTECTION.md). It targets `main` with no bypass, blocked deletion/force push, PRs and resolved conversations, and an up-to-date required `quality` check. Repository changes must follow the ordinary PR and checks route while activation remains pending.

# Reviewed financial operations

The app keeps model 3, API 3.3 and the ten business sheets / twelve business tables. Optional features use private typed technical tables. Their changes participate in the book revision, audit and request receipt; transactions are atomic and retries retain the same IDs. No private workbook values appear in fixtures.

## Typed metadata and compatibility

The read snapshot advertises `capabilities.archives`, `templates`, `payrollCorrection`, `contextualCorrection`, `fundTransfers`, plus `supportsPlanning` when the planning table exists. A client must show backend update guidance when a required capability is absent. Run the current preparation function on the bound test book before enabling newly installed features; preparation creates hidden technical tables without recording financial movements.

## Corrections and cancellations

`corregir_nomina` accepts the existing `movement` ID and the complete date, concept, account, category, net amount, gross amount, contribution, tax, other deductions and location. Known breakdown components must reconcile with net pay. Unknown components remain unknown. The income and payroll link retain their IDs.

`editar_movimiento` accepts the existing `movement`, a typed `kind`, and the corresponding ordinary operation fields. It atomically rebuilds the cash input and its debt/shared/refund reference, preserving the movement ID and checking all dependent records. It supports expense, income, transfer, received loan, repayment, shared recovery and expense refund. Payroll and investment cash require their dedicated editors. Remaining-eligibility pickers exclude the record being edited, and the final backend check still enforces chronological limits.

The review displays original and proposed values. Cancellation states the specific records and cash affected: payroll breakdown deletion retains its income, movement deletion removes its own payroll/investment/link records, goal deletion removes assignments, and grouped investment deletion recalculates remaining cash. Referenced master records cannot be deleted. A fund transfer must be canceled as a complete pair.

## Native fund-transfer formulas

Both funds must have an ISIN binding. Each actual units × NAV value must round to the same executed EUR settlement in cents. The reviewed `amount` records that settlement; when omitted, it is inferred from the outgoing raw value and still shown before confirmation. Raw outgoing and incoming values remain separately recorded and authenticated to a numerical tolerance of 0.00000001 EUR. Broker unit/NAV precision can therefore produce a disclosed subcent valuation residual without changing units, prices or contributions. Fees and tax are zero. The source must hold sufficient units at the transfer date. Old incomplete transfer metadata cannot be assumed to contain these raw values: the backend rejects a legacy 12-column transfer schema or an active record missing either raw value, rather than infer unsupported values or recalculate on a new basis. The operation writes cashless native `Venta` and `Compra` legs only when exact transfer metadata authenticates both legs. Other current cashless trades remain invalid. Existing prices are never changed by a transfer.

`costBasis` means signed **net contributions**, not tax acquisition cost. `investedBasis` carries the original model's cumulative gross contribution denominator. Each is allocated by outgoing units divided by available source units. The canonical chronological calculation recomputes these bases after earlier trades or product positions are corrected. A negative net contribution basis after a profitable withdrawal is retained honestly.

The current model's native product formulas were inspected read-only. Their contribution column is base cost plus purchases minus sales; return is value minus net contributions plus distributions; the return percentage denominator is base cost plus all purchases. The migration preserves these exact original expressions and adds typed transfer adjustments, bounded by valuation date. Product net contributions add `rawOut - costBasis` on the source and `costBasis - rawIn` on the destination. The gross denominator subtracts outgoing `investedBasis` and adds incoming `investedBasis - rawIn`. Thus contribution accounting remains exactly neutral even when both raw values round to the same settlement but differ because of broker precision. The actual market-value difference (`rawIn - rawOut`) is shown as a valuation residual; it creates no cash or income. Native monthly history capital receives the same dated net adjustment. Units, prices, cash, result expressions and unrelated native formulas retain their existing rules.

The first accepted transfer compares every targeted native contribution/percentage/history formula with the reviewed canonical model. A customized, missing or manually edited formula blocks the financial transaction. Readback comparison permits only Google's removal of optional quotes around ASCII sheet names outside string literals; numeric values, ranges and operators remain exact. Formula backup, migration version, updated formulas, both investment legs, transfer metadata, audit and receipt commit together. Migrated formulas are checked again before subsequent financial transactions. Capacity-generated history formulas retain the adjustment; copied reviewed product formulas can be registered without applying a second adjustment.

`restaurar_formulas_fondos` is a typed maintenance transaction with no input fields. It requires every transfer to be canceled first, verifies that current formulas still match the migration, restores canonical A1 originals for the current layout and marks backup records restored. This preserves financial formulas and results semantically; imported structured-reference text is retained in the backup, because writing that exact imported text through the API can produce formula parse errors. Original source formulas remain recorded. Manual formula edits are never overwritten. A fresh transfer can reapply the reviewed migration after restoration. This code does not authorize or perform a private workbook deployment or production activation. Native recalculation was verified on an isolated disposable copy using synthetic inputs; see OPERATIONS-VALIDATION.md. Deployment verification on the bound test copy remains part of release activation.

Distributions use the existing `rendimiento` process: one `Cobro` operation linked to one net `Rendimiento inversión` cash receipt. Native result includes distribution net once. Analytics keeps NAV change separate from distribution-inclusive total return, and neutralizes paired fund transfers as portfolio-internal flows.

## Table filters and export

Percentage bounds use displayed percentage units: `10` means `10%`, or native `0.10`. Filter rerenders retain keyboard focus; clearing removes all column bounds. CSV exports every row in the current filtered/sorted selection, including rows beyond the displayed page. It uses semicolons, quoted escaped fields, decimal commas, ISO dates and a UTF-8 BOM. Text beginning with a spreadsheet formula marker, including whitespace-prefixed markers, receives a leading apostrophe; numeric negative values remain numbers. Export never writes the workbook.
